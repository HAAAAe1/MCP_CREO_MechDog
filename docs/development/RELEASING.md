# 分支、版本与源码发布

`main` 保持可交付，开发使用 `codex/<条目>-<主题>` 短分支。提交标题指明 ID 和具体改变，例如 `BUG-002: retry atomic registry replacement`；无需引入复杂的长期分支或强制 Conventional Commits。

## 版本约定

`version.py` 是服务与源码版本的唯一手工入口；运行依赖锁定版本、种子包清单、工具输出和对外文档按各自契约核对一致。当前版本保持 `0.2.5`，DEV-001 尚未发布，不创建新标签或改写历史版本。

后续统一 `MAJOR.MINOR.PATCH`，候选版采用 `0.y.z-rc.1` 等格式。0.x 仍处于 API 形成阶段，本项目约定：兼容修复递增 PATCH，新增功能或不兼容接口调整递增 MINOR；不兼容变化必须附迁移说明。达到 1.0 后按标准的兼容性规则递增。开发条目可有目标版本；未承诺的工作写“未排期”，不能凭编号推断版本。

历史 `v0.22`、日期后缀标签及其附件保留原样。发布后标签所指源码和同名附件内容保持不变；任何变更通过新版本发布。[语义化版本规范](https://semver.org/lang/zh-CN/)

## 发布门槛

1. 明确本版条目、验收范围及未完成项；完成条目链接本次证据。记录受测提交和源码指纹，工作区有修改时不得仅用提交号代表源码。
2. 运行 `tools/dev_check.py`，检查所有适用单元回归。存量风格基线需显式说明，不宣称全库严格格式通过。
3. 在匹配 Creo 10/SDK/编译器的 Windows 环境运行原生发布回归。根据改动影响选择当前和历史套件，逐项记录命令、几何断言、参数编辑、保存擦除重载与适用回滚结果。完整回归未执行时列出具体未测模块，不把旧版本通过数改标为本版通过数。
4. 核对工具列表与 `capabilities.py`、文档、版本、种子数、种子指纹及兼容矩阵。Creo 12 的实验结果不能替代正式环境验收。
5. 使用 `tools/package.py` 与 `tools/package_seeds.py` 制作源码和种子附件；检查分发白名单、第三方许可、配置模板、开发配置、种子及 SHA256。从新目录解压并运行适用检查，随后在具备 SDK 的环境验收安装和建模。
6. 从实际验收源码建立版本标签及 Release，附版本说明、验收摘要、环境与范围限制。发布平台标记 Pre-release 与项目成熟度一致。

本地构建或检查不等于已发布。GitHub 操作和附件示例见 [原发布说明](../PUBLISH_GITHUB.md)；其 0.2.5 文件名为历史示例，未来按实际新版本生成，不重新发布相同版本的修改内容。

