## 1. 先确认：**BUG-007 的修复确实有效** ✅

这是本次最重要的正面结论，先写清楚，免得被下面的问题淹没。

升级前（0.2.5 与 0.3.0）直接放样 `creo_loft` / 计划 `op:"loft"` 会**挂死**在回调 DLL 加载处（实测 >270 s / >180 s，始终不终结，最终只被判 `unknown_outcome`）。

升级到 0.3.1 后，同一调用（3 截面直线，先建草图再 loft）：

| 指标 | 升级前 | 升级后 |
| --- | --- | --- |
| 结果 | 挂起，不终结 | **12 秒内 failed** |
| 错误信息 | 无（只有 `ProSelbufferClear()` 之后的静默） | **`BLEND_CALLBACK_SETUP_REQUIRED`**，含可操作指引 |
| 是否尝试加载 DLL | 是（卡在 `ProToolkitDllLoad`） | **否**（"No DLL load or Blend creation was attempted"） |

新版返回的原文（节选）：

```
BLEND_CALLBACK_SETUP_REQUIRED: No DLL load or Blend creation was attempted. The unsigned
Toolkit callback is not initialized, and Creo loader policy is prompt. Modeling never loads a
DLL, including under ALWAYS policy. Register and start the callback using Creo Auxiliary
Applications and <root>\build\blend_callback_setup.json (registry_file), review its DLL prompt
before modeling, then retry a new confirmed request. MCP never changes Creo security settings.
```

即：**从"静默挂死"变成了"快速失败 + 明确指引 + 明确声明不改安全策略"**。方向完全正确。

## 3. 问题详述

### 🟠 Q1 —— 常驻回调"升级即失效"，每次重编译都要在 Creo 重新注册

#### 代码依据

`src/creo_mechdog/blend_callback.py` 的 `prepare_callback()`：

```python
directory = build / "blend_callback" / dll_sha256          # 目录名 = DLL 的 sha256
target = directory / "callback.dll"
...
command = "MechDogBlend_" + dll_sha256[:24] + "_" + root_tag   # 命令名含 sha 前 24 位
```

本机实测产物：

```
build/blend_callback/96430578b3ac85f0d50393071c658fdff0e0f3025d04d4992d6a6b4c0233d637/
    callback.dll
    callback_bootstrap.json
    protk.dat
build/blend_callback.protk.dat   （快捷注册文件，内容指向上述 sha 目录）
```

生成的 `protk.dat`：

```
name MCP_CREO_MechDog Blend
startup dll
exec_file E:\...\build\blend_callback\96430578...\callback.dll
text_dir  E:\...\build\blend_callback\96430578...
allow_stop true
delay_start false
end
```

#### 影响

本次 0.3.0 → 0.3.1 **改了 `native/blend_sync.cpp`**，回调 DLL 随之变化：

| 版本 | `creo_blend_sync.dll` 大小 |
| --- | --- |
| 0.3.0 | 3,328,512 B |
| 0.3.1 | 3,384,832 B |

所以**目录路径与派生命令名都会变**（0.3.1 的 sha 是 `96430578…`）。对已经注册过回调的用户来说，每次升级后旧的注册指向的旧模块就不再是当前 DLL，**必须再去 Creo 辅助应用程序重新注册并启动一次**。

> 老实说明：本机**从未成功注册过**该回调（我无法操作 Creo GUI，也不应绕过安全确认），因此"重新注册"这个动作我**没有实测**。上面是基于产物路径与命令名都随 sha 变化的结构性推断；`name` 字段本身是固定的（`MCP_CREO_MechDog Blend`），Creo 是否允许同名重复注册、是否会提示冲突，需要作者或有 GUI 条件的协助者确认。

#### 建议

- 把回调副本目录改为**不含 sha 的稳定路径**（例如 `build/blend_callback/current/`），把"当前 DLL 是哪一个"记录在独立的清单文件里；
  这样升级后 Creo 里的注册条目仍然指向同一路径，只要 DLL 保持 ABI/协议兼容（`protocol: 2`）就无需重新注册。
  仅在**协议版本变化**时才需要重新注册 —— 这与代码里已经存在的 `protocol` 字段天然对齐。
- 若坚持 sha 目录，请至少：
  1. 在升级说明里**显著提示"本版需要重新注册常驻回调"**；
  2. 提供一个"旧版本回调已注册、当前 DLL 已变化"的检测与提示（现在只能等到放样失败才知道）。

### 🟠 Q2 —— 回调就绪状态无法预检

`creo_capabilities` 里确实新增了 `direct_blend_callback` 字段，但内容只覆盖**产物**层面：

```json
{
  "artifact_status": "prepared",
  "protocol": 2,
  "registry_file": ".../build/blend_callback/<sha>/protk.dat",
  "registry_shortcut": ".../build/blend_callback.protk.dat",
  "module_file": ".../build/blend_callback/<sha>/callback.dll",
  "dll_sha256": "96430578...",
  "manual_setup_when_not_loaded": true,
  "runtime_readiness": "Native worker checks the active Creo DLL handle and protocol for each loft; artifacts alone do not confirm readiness",
  "instruction": "In Creo Auxiliary Applications, register protk.dat and start this application; review any DLL prompt yourself. Modeling never changes the security policy."
}
```

它自己就说得很清楚：**"artifacts alone do not confirm readiness"**。但接口里**没有一个字段表达"当前 Creo 会话是否已加载该回调"**。

后果：调用方（尤其是 Agent）在提交放样前**无法判断是否会失败**，只能提交一次、拿一个 `BLEND_CALLBACK_SETUP_REQUIRED` 才知道。对自动化流程意味着"每次都要先故意失败一次"，或者干脆放弃直接放样路径。

#### 建议

- 在 `direct_blend_callback`（或 `creo_startup_status`）里增加一个原生探测得到的布尔/枚举，例如
  `loaded: true|false|unknown`、`loaded_dll_sha256`、`protocol_matched`；
- 由于文档已经说明"注册文件存在不等于已启动"，一个 `unknown`（例如会话不可探测时）比缺字段更有用；
- 这样 Agent 可以"先查再放样"，失败错误就成为真正的异常路径而不是常规路径。

#### 建议

- 要么在 release notes 落地时同步发 Release（仓库已经在 `docs/development/RELEASING.md` 里定了流程）；
- 要么在 README / 发布说明里明确"当前可交付版本已到 0.3.1，Release 待发"，避免使用者误判。

## 5. 本地绕过方式（未改动任何上游文件）

本机 `reg.exe` 被安全策略拦截 → `vcvars64.bat` 探测不到 Windows SDK → `cl` 报 `C1083: stdio.h`。
我维护本地脚本 `_local\rebuild-native.cmd`：在 `vcvars64` 之后**显式注入 SDK 的 include/lib**，
再执行与 `bridge.build_native()` 生成的**完全一致**的 cl/link 命令（worker + 回调 DLL 共 4 步），
成功后按新算法重写 `build\source.sha256` 与 `build\blend_sync_build.json`（后者会触发 `prepare_callback` 生成注册产物）。

**我没有、也不会去自动化 Creo 侧的 DLL 注册/安全确认** —— 这属于需要用户本人决定的安全动作，
本次仅把产物准备好并给出路径。
