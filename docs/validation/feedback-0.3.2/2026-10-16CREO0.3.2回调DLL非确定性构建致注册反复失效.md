## 1. 🔴 核心问题：回调 DLL **非确定性构建**，使"常驻注册"形同虚设

这是本次最重要的一条，直接击中 0.3.1 引入的常驻回调设计的可用性。

### 1.1 现象：源码不变，DLL 字节却每次都变

**事实链（全部实测）：**

1. 0.3.2 的 `native/blend_sync.cpp` 与 0.3.1 **逐字节相同**（sha256 均 `c2c6d4a6…`）；
2. 但 0.3.1 编出的 DLL 副本与 0.3.2 编出的**不同**：

| 来源 | 大小 | sha256 前 16 位 |
| --- | --- | --- |
| 0.3.1 编译副本（`build\blend_callback\96430578…`） | 3,384,832 B | `96430578b3ac85f0` |
| 0.3.2 编译副本（`build\blend_callback\0e46ef9d…`） | 3,384,832 B | `0e46ef9d76575785` |

3. 为排除偶然，我在**同一源码、同一机器、同一工具链**上连续编译两次：

```
trial A : 0e46ef9d76575785b7c806953326e47cf435a5c33893c0d51b23c8dcbcce56c7
trial B : c6dbf37b5335d7a663383c5bd9468069a788349272cc1c8a6859c873b4f261a9
两次编译 DLL 不同 -> 非确定性构建（复现）
```

### 1.2 与 0.3.1 设计叠加后的后果

`prepare_callback()`（0.3.1 引入）把 DLL 按 **sha256 建立不可变副本目录**，`protk.dat` 的 `exec_file`/`text_dir` 都指向该目录。

于是**每一次原生重编译**（哪怕 `blend_sync.cpp` 一行没改，甚至只是其它文件变更触发了 DLL 重链）都会：

1. 产出**新哈希**的 DLL → 新 sha 目录 → 新 `protk.dat`；
2. 使用户在 Creo「辅助应用程序」里注册的旧条目**指向失效路径**；
3. 用户必须**再次**人工注册并启动 —— 这正是 0.3.1 想用"常驻"来消除的负担。

本机现状就是活例：`build/blend_callback/` 下已经累积了 **3 个** sha 目录
（`96430578…`、`0e46ef9d…`、`e60521d2…`），其中只有最后一个与当前 DLL 匹配 —— **其中两个纯粹是重编译噪音产生的垃圾**，
但用户无从分辨（目录名就是哈希，没有"当前"标记）。

更糟的是我在复测时的真实遭遇：第二次编译后，当前 DLL（`c6dbf37b…`）与登记文件 `blend_sync_build.json` 记录的 `sha256`（`0e46ef9d…`）**不再匹配**，
按 `build_native()` 的逻辑下次又会触发重编 + 换目录。**"当前有效注册"随时可能悄悄失效**。

### 1.3 可能的根因方向（供作者参考，未逐一验证）

MSVC 输出通常因以下原因不确定：

- PE 头中的 **TimeDateStamp / 链接时间**（默认未开 `/Brepro`）；
- PDB 路径、**对象文件绝对路径**嵌入；
- `__DATE__`/`__TIME__` 或构建环境变量进入二进制（本项目源码里未见，但链接器/RT 消息表可能引入）。

常见修复是启用 **`/Brepro`**（配合 `/ZH:SHA_256`，MSVC 17.14 支持）让时间戳/校验和确定化；或对 DLL 做内容规范化。
即便不追求逐字节可复现，也应**避免把"编译产物哈希"当作用户可见的注册路径**（见 1.4）。

### 1.4 建议（按优先级）

1. **让注册路径与 DLL 哈希解耦**（最重要，且改动小）：
   副本目录用**固定名**（如 `build/blend_callback/current/`），`protk.dat` 指向它；
   "当前 DLL 是哪个哈希"记录到旁边的清单文件（`callback_manifest.json`）。
   这样升级/重编译后**Creo 注册条目继续有效**，仅当 `protocol` 版本变化时才需要重新注册 —— 与代码里已有的 `protocol: 2` 字段天然对齐。
2. 若哈希目录必须保留：**启动时/构建后清理过期的 sha 目录**（只留当前），否则目录会无限累积（本机 3 小时内已 3 个）；
3. 在 `blend_sync_build.json` 里同时记录**上次注册过的哈希**，当"当前 DLL ≠ 已注册哈希"时，在 `creo_capabilities.direct_blend_callback` 中给出**显式告警字段**（如 `registered_dll_stale: true`），而不是等放样失败；
4. 顺手项：可尝试 `/Brepro` 让 DLL 可复现，从根上消除"没改代码也换哈希"。

## 2. 🟠 次要问题：`prepare_callback()` 的不可变校验在哈希漂移下产生"死锁感"

`blend_callback.py` 对副本的校验是：

```python
if target.exists():
    if hashlib.sha256(target.read_bytes()).hexdigest() != dll_sha256:
        raise ValueError("Immutable Blend callback copy was changed; inspect it before setup")
```

配合"目录名 = sha256"的设计本意是防篡改。但结合 1 中的非确定性构建，实际会出现这样的序列：
登记文件写着 sha A → 用户或工具链重编译 → DLL 变成 sha B → `build_native()` 重编并生成 B 目录 → 一切自愈。
**但若任何外部流程只重编了 DLL 而没走 `build_native()`**（例如 CI 或用户手工 build），就会停在
"登记 A、实际 B、目录 A 里内容是 A"的不一致态，且报错只说"inspect it before setup"，不给出**自动修复路径**
（例如"检测到当前 DLL 与登记不符，已重建副本与注册文件，请在 Creo 重新注册"）。

**建议**：把这条 `ValueError` 的场景区分为"副本被外部改动"与"登记过期"，后者直接自动重建并更新 `blend_callback_setup.json`。
