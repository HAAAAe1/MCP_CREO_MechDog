## G0/G1 调查结论（对照外部报告）

外部报告称“MCP 协议层把 JSON null 传成空字符串”。在本仓锁定的 mcp 2.3.0 + pydantic 2.13.5 栈上逐层核实与真实 stdio 复现：

1. 工具 schema 正确声明 `expected_pending_job_id: anyOf[{string},{null}]`，default null（v0.3.4 与 HEAD 签名一致）。
2. SDK 校验管线（`FuncMetadata.validate_arguments`）实测：JSON null→None；省略→None；空串 `""`→原样 `""`；空白串→原样；字面字符串 `"null"`→被 `pre_parse_json` 预解析为 None（mcp 2.3.0 既定行为，协议测试锁定）；数字类型→协议层 ValidationError。**服务端任何一层都不存在 null→空串转换。**
3. 业务校验 `reconciliation.py` `_validate_evidence` 的 `model.get("pending_job") != pending`：模型无 pending 时 `None` 通过、`""` 拒绝。**空串产生与外部报告逐字一致的 "Stale expected_revision or expected_pending_job_id"。**
4. 结论：报告的失败形态与“客户端实际发送了空串”完全吻合；null 在服务端被转换的假设未能在受测身份上复现。外部客户端环境（Windows 10/Creo 9）未复测，该环境的客户端侧行为记为未验证。

## 修复（G2/G3，最小改动）

- `src/creo_mechdog/reconciliation.py` `apply()`：新增 `expected_pending_job_id` 形状校验——非空时必须匹配 32 位十六进制 job id；空串/空白/畸形值返回精确输入错误（引用实际收到的值），不再落入误导性 stale 拒绝。null/省略不受影响；非空 ID 的精确匹配语义不变。
- stale 错误拆分为两条可诊断消息（revision 与 pending 各自报告实际值与期望值）。
- `reconcile()` apply 必填错误消息与实际必填集合对齐（该字段 null 合法，不再列为“必填非空”）。
- `server.py`：`creo_reconcile_model` 的可空参数补充 schema 级 description，向客户端明确“pending_job 为 null 时发送 JSON null 或省略字段，禁止空串”。

不采用宽泛 truthiness 归一化；token 时效、所有者、revision、幂等与 busy 保护均未放宽。
