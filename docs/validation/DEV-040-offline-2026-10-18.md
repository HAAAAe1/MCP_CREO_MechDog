## BUG-057：本机未复现，尚不能选定修复

G1 在实现修改前连续执行 10 次：

```powershell
.\.venv\Scripts\python.exe -m unittest tests.unit.test_reconciliation
```

每次 21 项，10/10 轮通过，合计 210 次测试执行。完整输出为 `build/dev040_g1_baseline.json`。外部报告为 Windows 10 19045 / Python 3.13.14，本机系统和 Python 均不同；本机全过不能证伪外部失败，也不关闭 BUG-057。

初步纯打开对照在 absent、empty、one_byte 三种文件初态各做 1,000 次双线程竞争（每次两个 open），合计 6,000 次 `a+b` 打开全部通过，输出 `build/dev040_open_race.json`。受控持字节锁时，第二个 `a+b` 打开成功；主锁文件 unlink 则报 `PermissionError` / WinError 32。该结果证明“打开文件”和“取得字节锁”是两个阶段，不证明外部 Errno 13 的根因。

静态核对：`bridge.toolkit_lock` 从不删除 `toolkit.lock`，收尾删除的是另一个 `toolkit-owner.lock`；原失败用例先退出 ThreadPoolExecutor 再清理 TemporaryDirectory，没有直接证据表明本用例会重叠清理主锁。受控 sharing violation / delete-pending 能否产生类似错误，须与“实际失败路径制造了该状态”区分。

新增纯离线诊断入口：

```powershell
.\.venv\Scripts\python.exe tools\reproduce_toolkit_lock.py --iterations 1000 --output build\dev040-toolkit-lock-diagnostics.json
```

脚本只在 TemporaryDirectory 内执行文件操作与 Win32 对照，分别记录 open、locking 等阶段、errno 与底层 Windows 错误。它不连接 Creo、不读本机配置、不触碰仓库运行锁，可交给原反馈环境复核。本次 absent/empty/one_byte 各 1,000 轮自然并发竞争，均为一个 acquired、一个 lock_busy，没有 open_error；对已有文件的身份及内容均保持。

受控机制对照（不代表原故障已复现）：

| 条件 | Python 阶段/errno | 底层 Windows 错误 |
| --- | --- | --- |
| 其他句柄持字节锁 | locking / 13，归入 lock_busy | UCRT doserrno 33（LOCK_VIOLATION） |
| 独占共享句柄 | open / 13，不归入 busy | doserrno / CreateFileW 均为 32（SHARING_VIOLATION） |
| FileDispositionInfo 设置删除，FileStandardInfo 确认 DeletePending=true | open / 13，不归入 busy | doserrno / CreateFileW 均为 5（ACCESS_DENIED） |
| DeleteFileW + 共享 DELETE 的存活句柄 | 原句柄 DeletePending=true，但同路径可以创建新文件并取得新锁 | CreateFileW 成功 |

最后一项在本机说明删除共享主锁可能使同路径对应另一个文件对象；不能把 DeleteFileW 对照与阻止重新打开的传统 delete-pending 混为一谈，也不能仅凭 Errno 13 区分原因。

G3 当前决定：保留既有常驻锁文件及共享规则，不新增 open 重试，也不将打开失败改报 busy。共享 DELETE 允许持锁文件被删除并重新创建，可能破坏同一路径的互斥；在没有实际失败机制证据前不引入此风险。[Microsoft 字节锁说明](https://learn.microsoft.com/en-us/windows/win32/fileio/locking-and-unlocking-byte-ranges-in-files)也明确区分文件句柄与锁定的字节范围；此资料只辅助解释，不替代本机实验。

## BUG-059：阶段假设修正与已实现范围

修改前离线对照见 `build/dev040-bug059-baseline.json`：

| 场景 | 修改前观察 | 原生替代边界 |
| --- | --- | --- |
| token 在准入前过期 | 直接 ValueError，未接受新作业，也未新增恢复占位 | `_native` 调用次数 0 |
| 准入后会话选择配置变化 | failed / reconciliation_unconfirmed，已有 finished_at，但 recovery_pending 仍为该恢复 job | `_native` 调用次数 0 |
| 原生结果报告会话指纹变化 | unknown_outcome / reconciliation_unconfirmed，保留 recovery_pending | 合成原生返回，真实 `_native` 派发与结果检查路径执行，subprocess 被替代 |

原报告中的消息只在 `native/generic.cpp` 的 `reconcile_native` 中产生。实际顺序是 `connect_creo` → 取得并持久化会话指纹 → `reconcile_native` 内再次取得指纹 → 比较并拒绝，之后才是模型查找/擦除/载入。该消息位于 Toolkit 已开始之后，不能按“任何原生调用之前拒绝”来清保护。`worker_started` 则在 Python 调用 subprocess 前持久化，保守表示已经进入派发、原生可能开工，不保证进程确已启动。

本轮仅修改 Python：

- 证据/部署/会话选择/所有者等执行前检查使用带稳定 `reason` 的拒绝；未进入原生派发时返回 failed / reconciliation_refused，`failure_phase=before_native`。
- 在 Toolkit 通道锁内重新读取登记，仅当 `recovery_pending` 仍属于本 job 时清除此字段。保留原 pending_job、状态、revision、历史作业和幂等 journal；同键重放仍返回原失败作业。
- runner 启动失败也在准入锁内清理自己的恢复占位。清理失败返回 `recovery_pending_cleanup_error`，`recovery_pending_released=false` 并保留保护。未取得通道锁的执行拒绝以 `channel_admission` 说明，不能在锁外清理占位。
- 已进入原生派发的失败（含原生会话指纹拒绝、超时，以及原生成功后证据再校验失败）仍为 unknown_outcome / reconciliation_unconfirmed，`failure_phase=native_worker_started`，保留双重保护及原始结果消息；不靠错误文本判断是否执行。
- compact/full 轮询和幂等重放保留 reason、failure_phase、占位释放结果及清理错误。公开工具说明、README 和 [恢复契约](../MODEL_RECOVERY.md)同步此边界。

token 的 600 秒准入时效、四动作、空值契约、revision/pending/身份绑定和持久化提交语义不变。没有增加执行期 TTL 或自动续期；准入前过期仍直接拒绝，不凭空创建失败作业。原生指纹拒绝本轮只澄清阶段，不宣称已经确定为“原生无修改失败”。

## BUG-058：只读代码结论

完整审计见本机 `build/dev040_bug058_audit.md`：

- `creo_startup.py` 的 inventory（267～307 行）读取同一 Windows session 下的 PID、创建时间及映像路径，不读取 MainWindowHandle，也不枚举窗口。因此不能区分“有进程无主窗口”。
- 匹配旧进程存在时只探测并 waiting_for_connection；启动替代会话的分支要求没有现存进程（1005 行）。等待提示仍统一建议检查启动对话框（1076～1082 行），没有无窗口专用指引。
- launch_attempt 从历史恢复，仅在真正准备 launch 时递增（1041 行），retry 本身不递增。“旧匹配进程始终可见而单靠 retry 连增 5 次”无法由当前分支直接解释，需外部各时点 inventory/身份/历史证据。
- 无自动结束 Creo 路径。ShellExecute 返回的 DesktopLaunch 没有新进程的 PID/创建时间，launched_by_coordinator 布尔量不能作为自动清理归属证明。

该核对不改变协调器、不改变提示、不验证 Creo 9 的 -11 根因；BUG-058 继续待实机复现。
