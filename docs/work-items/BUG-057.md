# BUG-057：toolkit_lock 并发准入窗口在 Windows 报 PermissionError [Errno 13]

日期：2026-10-18。类型：缺陷。优先级：P1。状态：待复现。目标版本：未排期。

来源：外部 0.3.5 反馈（tag v0.3.5，commit 8ce644f），见[原件](../validation/FEEDBACK-0.3.5-2026-10-17.md)。环境：Windows 10 x64 (19045) / Python 3.13.14 x64 / MSVC 19.44.35229 + Windows SDK 10.0.26100 / Creo Parametric 9.0.0.0 Toolkit SDK。

## 报告现象（外部环境已证实）

`tools/test_unit.py` 307 个测试中仅 1 个失败，连续 3 次运行稳定复现（非偶发抖动）：

- 失败用例：`test_actual_competing_admissions_only_one_succeeds`（`unit.test_reconciliation.Reconciliation`）。该测试为 BUG-001 恢复功能引入（5628a33，2026-10-17），用双线程 Barrier 制造真实的 `rec.apply` 并发准入竞争。
- 失败位置：`src/creo_mechdog/reconciliation.py:577` `apply` → `bridge.py:291` `toolkit_lock` 内 `lock.open("a+b")` 报 `PermissionError: [Errno 13] Permission denied`，路径为测试 `TemporaryDirectory` 下的 `toolkit.lock`。
- 该失败为单元测试，不依赖 Creo 会话；当前开发分支 `bridge.py:291` 与反馈针对的 0.3.5 代码一致（2026-10-18 核对），本机可直接复现验证。

## 待核实根因（反馈为机制推测，无进程级现场）

- Windows `io.open`（CreateFile）默认不含 `FILE_SHARE_DELETE`；当 `toolkit.lock` 同路径名处于 delete-pending（如 `TemporaryDirectory` 递归清理与前序锁句柄交错）时，新 `open` 触发 sharing violation，映射为 Errno 13。
- `toolkit.lock` 本身在 `toolkit_lock` 收尾中从不 unlink（仅 `toolkit-owner.lock` 先删后解锁）；疑点在其他路径（测试夹具清理、用户手动删除、杀进程后句柄回收）是否会让该路径进入 delete-pending。
- 反馈推测本项与 BUG-001/BUG-056 通道失效"机制同源"。BUG-056 已于 2026-10-17 定位为跨批次遗留 nmsd 的会话信息失效并关闭归档；二者是否同源未核实，本项按独立缺陷跟踪，不据此重开 BUG-056。

## 范围

- 核实与修复限于 `bridge.toolkit_lock` 的锁文件打开与收尾路径，以及受影响单元测试的稳定性。
- 不改变通道语义：忙碌时仍立即拒绝（`ToolkitBusy`），不排队、不自动重试；Errno 13（打开失败）与 busy（持锁者存在）分开报错。
- 反馈建议的三个修复方向（锁文件常驻不删、`open` 外短重试、`FILE_SHARE_READ|WRITE|DELETE` 属性）仅作参考，须先在本机复现并取证后再定方案。
